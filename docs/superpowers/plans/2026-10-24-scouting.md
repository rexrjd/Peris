# Scouting Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for the inline domain work. Independent SQL and UI scopes may use the dispatching-parallel-agents workflow.

**Goal:** Dispatch scout-only reconnaissance with private snapshot reports and counter-scouting.

**Architecture:** Separate timed scout parties reuse existing route/crop/report mechanisms. Domain and authoritative SQL share the spec contract; UI emits commands and reads receipts.

**Tech Stack:** Existing React/TypeScript/Three.js, generated PostgreSQL and isolated PGlite.

**Spec:** `docs/superpowers/specs/2026-10-24-scouting-design.md`.

## Global constraints

- Root app only, all eleven factions, no dependencies or graphics exports.
- Base `bf2f8e7`, review branch `review/scouting`; no push or deployment.
- Scout-specific 35/20 strengths, Peris 3/2 casualty formula, only physically present scouts defend; no hero, loot, damage or progression.
- Private arrival snapshots; no failed-intel or clean-mission leaks. Thirty real-second cancellation and game-time travel/crop.

## Review focus

- Changed owners and returning destinations must not receive foreign troops or private intel.
- Troops detached, cancelled, starved and returned must conserve roles once.
- Reinforcement owners contribute their own research; clean missions leave no defender-visible receipt.
- Offline settlement must observe arrival state, not later production or troop changes.
- SQL focused reruns and old servers must preserve capability/receipt privacy.
